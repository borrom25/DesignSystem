# Строгое использование дизайн-системы в проекте

UI проекта собирается из публичных компонентов `borrom-ds-test`. Кнопки, поля, выбор, таблицы, модальные окна, уведомления и типографика используют ДС. Код приложения отвечает за данные, бизнес-логику, маршруты и композицию страницы.

## 1. Подключить последнюю опубликованную версию

При подключении и обновлении всегда выбирайте тег npm `latest`, используя менеджер пакетов проекта:

```bash
npm install borrom-ds-test@latest
# или
yarn add borrom-ds-test@latest
# или
pnpm add borrom-ds-test@latest
```

Проверьте фактически установленную версию:

```bash
npm ls borrom-ds-test
# или
yarn list --pattern borrom-ds-test
# или
pnpm list borrom-ds-test
```

Сохраните изменения зависимости и lockfile. `latest` выбирает актуальный опубликованный выпуск при установке/обновлении, а lockfile фиксирует выбранную версию для повторяемых сборок. Перед обновлением читайте [миграцию](migration-gitlab-c277eef5.md) и изменения выпуска.

Снимок API в текущей документации относится к `0.0.72`. Этот выпуск ещё в обработке, поэтому `latest` до завершения публикации может указывать на предыдущую версию. GitHub main и локальный плейграунд могут опережать npm. Проверяйте API по типам установленного пакета; возможность из ещё не опубликованной версии не заменяйте самодельным компонентом.

## 2. Подключить стили и провайдер

Импортируйте `borrom-ds-test/styles.css` один раз в точке входа. Оберните приложение в `UIKitProvider`: он подключает темы, размеры экрана, язык, модальные окна и уведомления. Если провайдер уже есть в корне, используйте его.

Минимальный пример для нового React-приложения:

```tsx
import { UIKitProvider, Text, Input, Button } from "borrom-ds-test";
import "borrom-ds-test/styles.css";

export function App() {
  return (
    <UIKitProvider>
      <main className="profile-page">
        <Text as="h1" variant="h2">Профиль</Text>
        <form className="profile-form" onSubmit={(event) => event.preventDefault()}>
          <Input name="name" label="Имя" placeholder="Введите имя" required />
          <Button htmlType="submit">Сохранить</Button>
        </form>
      </main>
    </UIKitProvider>
  );
}
```

Layout можно описывать в приложении. Используйте существующие токены ДС:

```css
.profile-page,
.profile-form {
  display: grid;
  gap: var(--generic-spacing-5);
}
```

Не переопределяйте через CSS внешний вид внутренних элементов ДС: цвета, размеры, радиусы, typography и состояния выбираются её публичными props и токенами. Подключение CSS и провайдера не требует повторной установки Tailwind в проект-потребитель только ради ДС. Совместимость с глобальными reset-стилями проекта проверяется на реальном экране.

## 3. Дать агенту обязательные правила

Скопируйте содержимое [шаблона для AGENTS.md](templates/consumer-agents.template.md) в `AGENTS.md` **проекта-потребителя**. Если файл уже существует, добавьте раздел с правилами ДС, сохранив остальные инструкции. Эти правила предназначены для приложения; создание новых компонентов внутри самой библиотеки описано отдельным workflow.

Для конкретной задачи можно дополнительно написать:

> Реализуй экран строго на `borrom-ds-test`. При подключении или обновлении используй `@latest` и проверь установленную версию. Сначала найди готовые компоненты и изучи их публичные props. Все UI-контролы и типографику собирай из ДС. Собственный CSS используй для layout и через существующие токены. Если компонента или состояния нет, зафиксируй gap и предложи расширение ДС; самодельную замену не создавай. Макет Figma связывай с готовыми компонентами через Link и Code Connect.

`AGENTS.md` задаёт рабочие правила агенту. При ревью проверяйте их выполнение по импортам, JSX и CSS; сама установка пакета не ограничивает способы написания UI.

## 4. Перед созданием экрана найти готовый API

1. Откройте [каталог компонентов](public-components.md) и документы нужных компонентов. Проверьте props по TypeScript установленного пакета.
2. Выберите готовые компоненты, их variants, sizes, states и slots. Для составных компонентов используйте публичную композицию: например, `Popover.Trigger` / `Popover.Content`.
3. Импортируйте из `borrom-ds-test`, стили — из `borrom-ds-test/styles.css`. Внутренние пути `src`, `dist` и неэкспортируемые компоненты не являются API потребителя.
4. Свяжите значения и обработчики с логикой приложения. Не копируйте runtime ДС в приложение, не создавайте параллельные `Button`, `Input`, `Select`, `Table` или `Modal` с тем же назначением.
5. Для отсутствующего компонента или состояния запишите gap: что требуется, какие готовые варианты рассмотрены и какого API не хватает. Предложите расширение библиотеки. Остановите зависимую часть реализации и продолжайте независимые части экрана.

Обёртка для бизнес-логики допустима, если она использует готовый компонент ДС, сохраняет его визуальный контракт и не реализует собственный аналог. Например, поле имени может связывать `Input` с формой приложения.

## 5. Если есть макет Figma

Сначала откройте Link компонента и Code Connect. Найдите соответствующий публичный компонент и настройте его реальными props. Сохраните вложенные компоненты, слоты и состояния. Raw-значения макета сопоставляйте с существующими токенами ДС; неизвестное соответствие фиксируйте как assumption, а не переносите произвольные числа в стили.

Code Connect помогает выбрать компонент и props; доступность импорта проверяется по установленному пакету. Если Figma шире текущего API, опишите расхождение. Готовый компонент не нужно перерисовывать по слоям макета.

Подробности: [работа с Git-ссылкой из Figma](../Правила%20работы%20с%20Git-ссылкой%20из%20Figma.md), [статус связок](figma-component-connections.md), [публикация Code Connect](figma-publication.md).

## 6. Проверить готовый экран

- Все контролы и типографика используют публичные компоненты ДС; собственные блоки отвечают за layout и бизнес-композицию.
- Props существуют в установленной версии. Нет импортов внутренних модулей и выдуманных variants.
- Нет CSS-селекторов, `!important`, inline-стилей или utility-классов, меняющих визуальный контракт компонентов ДС.
- Проверены используемые состояния: ввод, выбор, ошибки, disabled/loading, открытие и закрытие модальных окон, навигация с клавиатуры, темы и адаптивность.
- Пройдены существующие проверки типов, lint и сборки **проекта-потребителя**. В приложении проверен реальный экран; Storybook ДС используется как эталон состояний.
- В результате задачи указаны установленная версия ДС, использованные компоненты, выполненные проверки и оставшиеся gaps.
