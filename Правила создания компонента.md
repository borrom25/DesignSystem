# Правила создания компонента

## Когда читать этот документ

Читать этот файл, когда задача связана с созданием или существенным обновлением компонента:

- нужно создать новый компонент;
- нужно обновить компонент по Figma;
- нужно добавить variants, states, sizes или slots;
- нужно изменить публичный API компонента;
- нужно подготовить компонент к Storybook или Code Connect.

Для мелких bugfix-правок можно читать только сам компонент, его types, styles и story.

Если Figma-компонент содержит ссылку на Git/репозиторий, сначала читать `Правила работы с Git-ссылкой из Figma.md`. В этом случае основная задача - импортировать и настроить готовый компонент, а не создавать новый.

## Главный принцип

Компонент должен повторять текущую структуру проекта. Не придумывать новую организацию файлов, если соседние компоненты уже показывают подходящий паттерн.

Минимальная структура:

```text
src/components/<Component>/
  <Component>.tsx
  <Component>.types.ts
  index.ts
  styles/
    index.ts
    base.ts
```

Если компонент простой и соседние аналоги не используют `styles/`, можно оставить стили в компоненте, но по умолчанию предпочитать существующий паттерн со `styles`.

Story:

```text
src/stories/<Component>.stories.tsx
```

Если нужен Code Connect:

```text
src/components/<Component>/<Component>.figma.js
```

## Источники истины

Перед созданием компонента читать:

1. похожие компоненты в `src/components`;
2. их `*.types.ts`;
3. их `styles`;
4. stories в `src/stories`;
5. `src/tokens`;
6. `src/styles`;
7. `src/index.ts` и index-файлы, если компонент должен экспортироваться.

Если компонент создается из Figma, Figma задает структуру, variants, states и visual intent, но реализация должна использовать токены и паттерны проекта.

## Перед созданием нового компонента

Всегда проверить:

1. существует ли уже компонент в `src/components`;
2. можно ли расширить существующий компонент без ломки API;
3. можно ли собрать новый сценарий композицией существующих компонентов;
4. есть ли похожий компонент с нужными variants/states;
5. есть ли готовые токены для размеров, цветов, typography, radius, stroke и effects.

Если компонент уже существует:

- переиспользовать или расширить его;
- не создавать дубликат;
- не дублировать API;
- не переименовывать variants без необходимости;
- изменения делать совместимыми с существующими props.

Если компонент найден по Git-ссылке из Figma:

- открыть его `*.tsx`, `*.types.ts`, `styles` и story;
- понять публичный API;
- использовать import готового компонента;
- сопоставить Figma variants/states с props;
- верстать вручную только layout вокруг компонента или отсутствующие screen-level части.

## Структура файлов

### `<Component>.tsx`

Runtime React-компонент:

- импортирует типы из `./<Component>.types`;
- импортирует styles из `./styles`;
- не содержит больших таблиц style variants, если они уже вынесены в `styles`;
- использует существующие helpers (`clsx`, `tailwind-merge`, shared utilities), если такой паттерн есть рядом;
- содержит accessibility attributes для интерактивных элементов.

### `<Component>.types.ts`

Публичный API:

- `ComponentProps`;
- enum-like unions или imports из общих типов;
- отдельные internal types только если они действительно нужны;
- не смешивать runtime logic и типы.

### `index.ts`

Локальный export:

```ts
export { Component } from "./Component";
export type { ComponentProps } from "./Component.types";
```

Если компонент экспортирует constants или дополнительные типы, повторять стиль соседних компонентов.

### `styles/`

Стили компонента:

- `base.ts` - базовые классы;
- `sizes.ts` - размеры;
- `variants.ts` или `styles/variants/*` - variants;
- `states.ts` - states;
- `index.ts` - единая точка сборки styles.

Создавать только те файлы, которые реально нужны. Не дробить простой компонент ради формы.

### Storybook

Story должна:

- покрывать основные variants;
- показывать sizes и states;
- демонстрировать disabled/loading/error/selected, если они есть;
- использовать публичный API компонента;
- не импортировать внутренние файлы без необходимости.

## Работа с Figma

Нужно анализировать:

- все вложенные слои;
- auto-layout;
- padding и gap;
- constraints;
- variants;
- component properties;
- interactive states;
- typography;
- color tokens и semantic tokens;
- effects, radius, stroke, opacity;
- hidden layers, overlays и nested instances;
- icon containers;
- slot-like структуры;
- conditional blocks;
- тексты и property names, которые должны стать props.

Не начинать писать компонент до анализа variants, states и token mapping.

Если в Figma есть Git-ссылка на компонент, не использовать visual fallback как основу реализации. Сначала открыть ссылку, прочитать компонент и собрать нужное состояние через props.

## Работа с variants и states

Реализовывать все варианты, которые есть в Figma и относятся к публичному поведению компонента.

Частые группы:

- size;
- variant/type/appearance;
- color/tone;
- state;
- loading;
- disabled;
- error/invalid;
- selected/active/checked;
- icon и icon-only;
- filled/empty;
- hover/focus/pressed.

Если Figma содержит state, он должен быть доступен в коде либо как runtime-состояние, либо как story state для визуальной проверки.

## Работа с токенами

В реализации использовать проектные токены и существующие style helpers.

Основные источники:

- `src/tokens`;
- `src/styles`;
- `src/components/<Component>/styles`;
- styles похожих компонентов.

Запрещено:

- подставлять raw-значения из Figma напрямую, если есть токен;
- использовать произвольные значения вручную без причины;
- создавать параллельную token system;
- молча придумывать новый токен.

Если точного токена нет:

- использовать ближайший подходящий проектный токен;
- отметить mapping как `temporary mapping` или `assumption`;
- не скрывать расхождение от пользователя.

## Работа с layout

Auto-layout из Figma переносить в flex/grid максимально близко, сохраняя:

- direction;
- gap;
- alignment;
- padding;
- distribution;
- grow/shrink;
- min/max width;
- min/max height;
- wrapper-элементы, если они несут смысл состояния, слота или выравнивания.

Не схлопывать вложенные контейнеры, если они отвечают за slot, icon container, label/input stack, counter, helper text, clear action или другой смысловой слой.

## Работа с иконками

Сначала искать существующий паттерн в соседних компонентах. В проекте используется `lucide-react`, поэтому для новых стандартных иконок предпочитать его, если нет собственной icon system или готового компонента.

Нужно сохранять:

- размеры icon container;
- alignment;
- `aria-hidden` для декоративных иконок;
- доступное имя для icon-only действий.

## Code Connect

Если задача включает Figma Code Connect или компонент должен быть доступен для Figma mapping:

- читать `Правила создания Code Connect.md`;
- добавлять `<Component>.figma.js` рядом с runtime file;
- синхронизировать props с реальным API компонента;
- не создавать mapping, который требует несуществующих props.

## Проверка качества

Хорошая реализация:

- повторяет структуру соседних компонентов;
- использует existing components и shared helpers;
- использует tokens/styles проекта;
- поддерживает релевантные variants и states;
- имеет story;
- не ломает существующие props;
- содержит явные assumptions для отсутствующих токенов.

Плохая реализация:

- создает новую структуру без причины;
- "примерно похожа" на Figma;
- верстает вручную готовый компонент, на который есть Git-ссылка;
- игнорирует states или variants;
- хардкодит значения без необходимости;
- создает дубли компонентов;
- не обновляет exports или story;
- меняет публичный API без проверки usages.

## Финальная цель

Цель не просто сделать похожий компонент, а добавить системный, переиспользуемый компонент, который вписывается в текущую структуру `src/components`, проверяется через Storybook и может быть связан с Figma через Code Connect.
